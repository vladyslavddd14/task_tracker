# Специфікація: Task Tracker (Lab 12)

Версія: 1.0 · Стек: C# (ASP.NET Core) + React + PostgreSQL · Запуск: Docker Compose

---

## 1. Загальний опис

**Task Tracker** — багатокористувацький веб-застосунок для ведення задач зі статусами, пріоритетами, дедлайнами, тегами, підзадачами та Markdown-нотатками. Задачі можна переглядати списком, kanban-дошкою та календарем.

**Рівні виконання:** Basic ✅ · Standard ✅ · Advanced: Kanban Web UI, Subtasks, Markdown Notes, Multi-user, Calendar View.

### 1.1. Особистий твіст («Make it yours»): трекер, який налаштовується під будь-яку роль

Трекер не прив'язаний до однієї професії. Користувач під час реєстрації (або пізніше в налаштуваннях) обирає **шаблон профілю**, який налаштовує інструмент під його цілі:

| Шаблон | Теги за замовчуванням | Власні поля задач (приклад) |
|---|---|---|
| Універсальний | — | — |
| Студент | `лекція`, `лабораторна`, `екзамен` | «Предмет» (текст), «Оцінка» (число) |
| Фрілансер | `клієнт`, `рахунок` | «Клієнт» (текст), «Ставка/год» (число), «Виставлено рахунок» (прапорець) |
| Тренування | `біг`, `зал` | «Дистанція, км» (число), «Тривалість, хв» (число) |

Крім шаблонів, користувач може створювати **власні поля** (custom fields) для своїх задач. Це дає змогу кожному використовувати трекер у власних цілях без зміни коду.

**Обґрунтування для захисту:** більшість трекерів змушують людину підлаштовуватися під інструмент; тут інструмент підлаштовується під людину, і при цьому залишається простим, бо додаткові поля необов'язкові.

## 3. Архітектура (Clean Architecture)

Залежності спрямовані тільки всередину: `Api → Application → Domain`, `Infrastructure → Application → Domain`.

```
task-tracker/
  README.md
  SPEC.md
  docker-compose.yml
  .env.example
  backend/
    TaskTracker.sln
    src/
      TaskTracker.Domain/            # сутності, enum-и, доменні правила, винятки. Без залежностей
      TaskTracker.Application/       # use cases (сервіси/handlers), DTO, інтерфейси репозиторіїв,
                                     # валідатори, інтерфейси IPasswordHasher, ITokenService, IClock
      TaskTracker.Infrastructure/    # EF Core DbContext, конфігурації сутностей, міграції, репозиторії,
                                     # JWT, хешер паролів, системний годинник, seed
      TaskTracker.Api/               # контролери, middleware (обробка помилок), DI, Program.cs, Swagger
    tests/
      TaskTracker.Domain.Tests/
      TaskTracker.Application.Tests/
      TaskTracker.Api.IntegrationTests/
  frontend/
    Dockerfile
    nginx.conf
    src/
      api/          # типізований HTTP-клієнт
      features/     # auth, tasks, board, calendar, tags, settings
      components/
      pages/
      hooks/
  docs/
    screenshots/
```

### 3.1. Правила шарів

- **Domain** не знає про EF Core, HTTP, JWT. Містить сутності з поведінкою (зміна статусу, додавання підзадачі, валідація інваріантів).
- **Application** містить сценарії використання, які оперують інтерфейсами. Контролери лише викликають їх і відображають результат у HTTP.
- **Infrastructure** реалізує інтерфейси: репозиторії, доступ до БД, токени, хешування.
- **Api** не містить бізнес-логіки: тільки маршрутизація, автентифікація, перетворення помилок на коди відповіді.
- Усі операції над задачами **завжди фільтруються за `UserId`** поточного користувача (ізоляція даних на рівні Application/репозиторію, а не лише контролера).

## 4. Модель даних

Усі id: `Guid`. Усі часові мітки: UTC (`timestamptz`), ISO 8601 в API.

### 4.1. Сутності

**User**
- `Id`, `Email` (унікальний, нижній регістр), `PasswordHash`, `DisplayName`, `TimeZoneId` (IANA, напр. `Europe/Kyiv`), `ProfileTemplate` (enum), `CreatedAt`

**TaskItem**
- `Id`, `UserId`
- `Title` (обов'язково, 1–200 символів)
- `Description` (необов'язково, до 2000 символів, звичайний текст)
- `NotesMarkdown` (необов'язково, до 20 000 символів)
- `Status`: `Todo | InProgress | Done`
- `Priority`: `Low | Medium | High` (за замовчуванням `Medium`)
- `Deadline` (`DateOnly`, необов'язково: календарна дата без часу, щоб уникнути зсувів на день через часові пояси)
- `Position` (число для порядку в колонці kanban)
- `CreatedAt`, `UpdatedAt`, `CompletedAt` (необов'язково)

**Subtask**
- `Id`, `TaskItemId`, `Title` (1–200), `IsDone`, `Position`, `CreatedAt`
- Один рівень вкладеності (підзадача не має власних підзадач).

**Tag**
- `Id`, `UserId`, `Name` (1–30 символів, унікальне в межах користувача без урахування регістру), `Color` (необов'язково, hex)

**TaskTag** — зв'язок багато-до-багатьох `TaskItem` ↔ `Tag`.

**StatusTransition**
- `Id`, `TaskItemId`, `FromStatus`, `ToStatus`, `ChangedAt`
- Створюється при кожній зміні статусу (вимога Basic: час переходу).

**CustomFieldDefinition** (для твіста)
- `Id`, `UserId`, `Name` (1–40), `Type`: `Text | Number | Checkbox | Date`, `Position`

**CustomFieldValue**
- `Id`, `TaskItemId`, `CustomFieldDefinitionId`, `Value` (зберігається як текст, інтерпретується за типом поля)

### 4.2. Доменні інваріанти

- Заголовок не порожній і не складається лише з пробілів; значення обрізається по краях.
- При переході в `Done` встановлюється `CompletedAt`; при виході з `Done` він очищається.
- Дозволені переходи між статусами: **будь-який → будь-який** (потрібно для drag-and-drop в kanban), кожен перехід записується в `StatusTransition`.
- Задача вважається **простроченою**, якщо `Deadline < сьогодні` (у часовому поясі користувача) і `Status != Done`.
- Видалення задачі каскадно видаляє підзадачі, зв'язки з тегами, переходи та значення власних полів.
- Видалення тега прибирає його лише зі зв'язків; задачі залишаються.
- Видалення власного поля видаляє всі його значення.

## 5. Функціональні вимоги

Пріоритети: **MUST** — обов'язково, **SHOULD** — бажано, **COULD** — якщо буде час.

### 5.1. Автентифікація та multi-user (MUST)

- **FR-A1.** Реєстрація: email + пароль + відображуване ім'я. Email унікальний. Пароль ≥ 8 символів.
- **FR-A2.** Вхід: email + пароль → JWT access-токен (час життя 60 хвилин, налаштовується).
- **FR-A3.** Кожен користувач бачить і змінює **лише свої** дані. Спроба доступу до чужої задачі повертає `404`.
- **FR-A4.** Паролі зберігаються лише у вигляді солоного хешу.
- **FR-A5.** Фронтенд зберігає токен, додає його до запитів, при `401` перенаправляє на сторінку входу.
- **FR-A6 (SHOULD).** Сторінка профілю: зміна імені, часового поясу, шаблону профілю, пароля.

### 5.2. Рівень Basic

- **FR-B1.** Створення задачі (заголовок + статус; за замовчуванням `Todo`).
- **FR-B2.** Перегляд списку задач.
- **FR-B3.** Зміна статусу `Todo → InProgress → Done` (та назад).
- **FR-B4.** Видалення задачі (з підтвердженням у UI).
- **FR-B5.** Дані зберігаються в PostgreSQL; після перезапуску застосунку та контейнерів (без видалення volume) все на місці.
- **FR-B6.** Порожній заголовок відхиляється (і на фронтенді, і на бекенді).
- **FR-B7.** Кожна задача має `CreatedAt`; кожна зміна статусу записується з часом.

### 5.3. Рівень Standard

- **FR-S1.** Повний CRUD, включно з редагуванням усіх полів задачі.
- **FR-S2.** Три статуси з записом переходів (див. 4.2).
- **FR-S3.** Пріоритет (`Low/Medium/High`) і дедлайн.
- **FR-S4.** Теги: задача може мати кілька тегів; створення, перейменування, видалення тегів.
- **FR-S5.** Фільтрація (комбінується через AND):
  - за статусом (один або кілька);
  - за пріоритетом;
  - за тегом (один або кілька);
  - за дедлайном: `overdue` (прострочені), `today`, `upcoming` (майбутні), `none` (без дедлайну), або діапазон дат;
  - за текстовим пошуком (по заголовку, опису та нотатках, без урахування регістру).
- **FR-S6.** Сортування: за пріоритетом (за замовчуванням: High → Low), за дедлайном, за датою створення, за назвою.
- **FR-S7.** **Вигляд «Сьогодні»**: задачі з дедлайном сьогодні + прострочені, які не виконані; відсортовані за пріоритетом. Це стартова сторінка після входу.
- **FR-S8.** Прострочені задачі візуально виділені (червоний).
- **FR-S9.** Безпечне збереження: усі зміни виконуються в транзакціях PostgreSQL; складні операції (наприклад, зміна статусу + запис переходу) атомарні.
- **FR-S10.** Чисте розділення модулів за Clean Architecture (розділ 3).
- **FR-S11 (SHOULD).** Пагінація списку (`page`, `pageSize`, за замовчуванням 50).

### 5.4. Advanced: Kanban Web UI

- **FR-K1.** Дошка з трьома колонками: «До виконання», «В роботі», «Виконано».
- **FR-K2.** Drag-and-drop картки між колонками змінює статус (з записом переходу) та зберігає позицію.
- **FR-K3.** Drag-and-drop всередині колонки змінює порядок (`Position`); порядок зберігається в БД.
- **FR-K4.** Картка показує: заголовок, пріоритет, дедлайн, теги, прогрес підзадач.
- **FR-K5.** Дошка підтримує ті самі фільтри, що і список.
- **FR-K6.** Оптимістичне оновлення UI з відкатом при помилці сервера.
- **FR-K7 (SHOULD).** Клавіатурна доступність перетягування (dnd-kit keyboard sensor).

### 5.5. Advanced: Subtasks

- **FR-T1.** До задачі можна додавати, редагувати, відмічати, видаляти та впорядковувати підзадачі.
- **FR-T2.** Прогрес = `виконані / усі`; показується прогрес-баром у списку, на картці kanban та в деталях.
- **FR-T3.** Відмітка всіх підзадач виконаними **не змінює статус** батьківської задачі автоматично; натомість UI пропонує «Позначити задачу виконаною».
- **FR-T4.** Максимум 50 підзадач на задачу.

### 5.6. Advanced: Markdown Notes

- **FR-M1.** Кожна задача має поле нотаток у Markdown.
- **FR-M2.** Редактор із двома режимами: «Редагувати» / «Перегляд» (або side-by-side).
- **FR-M3.** Підтримка: заголовки, списки, чекбокси, код, посилання, цитати, таблиці (GFM).
- **FR-M4.** **Безпека:** HTML у Markdown санітизується (без виконання скриптів, `javascript:`-посилань тощо). Сирий HTML вимкнений або фільтрується через `rehype-sanitize`.
- **FR-M5.** Пошук (FR-S5) враховує текст нотаток.

### 5.7. Advanced: Calendar View

- **FR-C1.** Перемикач режимів відображення: **Список · Kanban · Календар** (вибір запам'ятовується в браузері).
- **FR-C2.** Календар: місячний та тижневий вигляд; задачі розміщуються в клітинках за `Deadline`.
- **FR-C3.** Навігація: попередній/наступний період, кнопка «Сьогодні».
- **FR-C4.** Колір позначки залежить від пріоритету або статусу; виконані задачі приглушені; прострочені виділені.
- **FR-C5.** Клік по задачі відкриває її деталі.
- **FR-C6.** Задачі без дедлайну показуються в бічній панелі «Без дати».
- **FR-C7 (SHOULD).** Перетягування задачі на іншу дату змінює дедлайн.
- **FR-C8.** Календар враховує активні фільтри.

### 5.8. Твіст: профілі та власні поля

- **FR-P1.** При реєстрації користувач обирає шаблон профілю (розділ 1.1) або «Універсальний». Вибір можна змінити в налаштуваннях.
- **FR-P2.** Застосування шаблону створює набір тегів і власних полів за замовчуванням. Вже наявні дані **не видаляються**; дублікати за назвою пропускаються.
- **FR-P3.** Користувач може створювати, перейменовувати, змінювати порядок та видаляти власні поля (типи: текст, число, прапорець, дата).
- **FR-P4.** Власні поля відображаються у формі та деталях задачі; значення типізовані й валідуються за типом.
- **FR-P5 (SHOULD).** Фільтр за значенням власного поля (як мінімум для прапорця та тексту).
- **FR-P6 (COULD).** Експорт задач у CSV (включно з власними полями).

### 5.9. Демо-дані

- **FR-D1.** Команда `docker compose` має опційний профіль/змінну `SEED_DEMO=true`, яка створює демо-користувача з реалістичними задачами (різні статуси, пріоритети, дедлайни, теги, підзадачі, нотатки). Реальні, а не «Task 1 / Task 2».

## 6. REST API

Базовий шлях `/api`. Формат: JSON. Усі маршрути, крім `auth/*`, потребують `Authorization: Bearer <token>`.

### 6.1. Auth та профіль

| Метод | Шлях | Опис |
|---|---|---|
| POST | `/api/auth/register` | Реєстрація |
| POST | `/api/auth/login` | Вхід, повертає токен |
| GET | `/api/me` | Поточний користувач |
| PUT | `/api/me` | Оновлення профілю |
| PUT | `/api/me/password` | Зміна пароля |
| POST | `/api/me/apply-template` | Застосування шаблону профілю |

### 6.2. Задачі

| Метод | Шлях | Опис |
|---|---|---|
| GET | `/api/tasks` | Список з фільтрами, сортуванням, пагінацією |
| GET | `/api/tasks/today` | Вигляд «Сьогодні» |
| GET | `/api/tasks/{id}` | Деталі задачі (з підзадачами, тегами, нотатками, власними полями) |
| POST | `/api/tasks` | Створення |
| PUT | `/api/tasks/{id}` | Редагування |
| PATCH | `/api/tasks/{id}/status` | Зміна статусу |
| PATCH | `/api/tasks/{id}/move` | Зміна статусу та позиції (kanban) |
| DELETE | `/api/tasks/{id}` | Видалення |

**Query-параметри `GET /api/tasks`:** `status` (повторюваний), `priority`, `tagId` (повторюваний), `deadline` (`overdue|today|upcoming|none`), `deadlineFrom`, `deadlineTo`, `q`, `sort` (`priority|deadline|createdAt|title`), `dir` (`asc|desc`), `page`, `pageSize`.

### 6.3. Підзадачі

| Метод | Шлях | Опис |
|---|---|---|
| POST | `/api/tasks/{id}/subtasks` | Додати |
| PUT | `/api/tasks/{id}/subtasks/{subtaskId}` | Редагувати / відмітити |
| DELETE | `/api/tasks/{id}/subtasks/{subtaskId}` | Видалити |
| PATCH | `/api/tasks/{id}/subtasks/reorder` | Змінити порядок |

### 6.4. Теги та власні поля

| Метод | Шлях | Опис |
|---|---|---|
| GET / POST | `/api/tags` | Список / створення |
| PUT / DELETE | `/api/tags/{id}` | Перейменування / видалення |
| GET / POST | `/api/custom-fields` | Список / створення |
| PUT / DELETE | `/api/custom-fields/{id}` | Редагування / видалення |

### 6.5. Календар

| Метод | Шлях | Опис |
|---|---|---|
| GET | `/api/tasks/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD` | Задачі з дедлайном у діапазоні (підтримує ті самі фільтри) |

### 6.6. Службове

| Метод | Шлях | Опис |
|---|---|---|
| GET | `/health` | Перевірка стану (для healthcheck у Docker) |
| GET | `/swagger` | Документація API (лише в Development) |

### 6.7. Коди відповідей та формат помилок

- `200/201/204` — успіх; `400` — помилка валідації; `401` — не автентифіковано; `404` — не знайдено (включно з чужими ресурсами); `409` — конфлікт (дублікат email/тега); `500` — внутрішня помилка.
- Помилки у форматі **RFC 7807 Problem Details**; для валідації додається словник `errors` по полях. Стек-трейси клієнту не передаються.

## 7. Валідація

| Поле | Правило |
|---|---|
| Email | коректний формат, ≤ 254 символів |
| Пароль | ≥ 8 символів, ≤ 100 |
| Заголовок задачі / підзадачі | не порожній після trim, ≤ 200 |
| Опис | ≤ 2000 |
| Нотатки | ≤ 20 000 |
| Тег | 1–30, унікальний у межах користувача (без урахування регістру) |
| Власне поле | назва 1–40, унікальна в межах користувача; тип із переліку |
| Значення власного поля | відповідає типу (число — число, дата — ISO-дата тощо) |
| `pageSize` | 1–200 |

Валідація виконується на бекенді (джерело істини) **і** на фронтенді (для зручності користувача).

## 9. Docker та конфігурація

### 9.1. Сервіси `docker-compose.yml`

| Сервіс | Образ / збірка | Призначення |
|---|---|---|
| `db` | `postgres:16-alpine` | База даних, named volume `pgdata`, healthcheck `pg_isready` |
| `api` | multi-stage build (`dotnet sdk` → `aspnet`) | Backend; залежить від `db` (condition: `service_healthy`); застосовує міграції при старті |
| `web` | multi-stage build (`node` → `nginx`) | Збірка React та роздача статики; проксіює `/api` на `api` |

### 9.2. Вимоги

- **NFR-D1.** Запуск однією командою: `docker compose up --build` на чистій машині (потрібні лише Docker і Compose).
- **NFR-D2.** Конфігурація через змінні середовища (`.env`, шаблон у `.env.example`): параметри БД, `JWT__Secret`, `JWT__ExpiresMinutes`, `SEED_DEMO`, порти. У репозиторії немає реальних секретів.
- **NFR-D3.** Міграції EF Core застосовуються автоматично при старті `api`; повторний запуск безпечний (ідемпотентний).
- **NFR-D4.** Дані переживають `docker compose down` (без `-v`) і перезапуск машини.
- **NFR-D5.** Порожня БД на першому запуску створюється без помилок.
- **NFR-D6.** Користувач у контейнері `api` не root; образи збираються з використанням `.dockerignore`.
- **NFR-D7.** Frontend і backend працюють через одну точку входу (nginx), тому CORS у продакшн-режимі не потрібен; для локальної розробки (`vite dev`) CORS налаштований явно.
- **NFR-D8.** У README описано, як запустити тільки БД в Docker, а api/web локально для розробки.

## 10. Нефункціональні вимоги

- **Продуктивність:** типові запити списку (до 1000 задач у користувача) відповідають < 300 мс; створено індекси на `(UserId, Status)`, `(UserId, Deadline)`, унікальні індекси на `Users.Email` та `(UserId, lower(Tag.Name))`; для пошуку достатньо `ILIKE`.
- **Безпека:** хешування паролів, JWT-підпис, перевірка власності ресурсів, санітизація Markdown, параметризовані запити (EF Core), відсутність секретів у коді, обмеження розміру тіла запиту.
- **Надійність:** глобальний обробник помилок, транзакції, цілісність через зовнішні ключі та каскадні правила; конкурентні оновлення не псують дані (мінімум: last-write-wins з оновленням `UpdatedAt`; SHOULD: оптимістичний контроль через `xmin`/`RowVersion`).
- **Логування:** структуроване логування (Serilog або вбудований `ILogger`), без паролів і токенів у логах.
- **Час і дати:** зберігання в UTC; `Deadline` — календарна дата; обчислення «сьогодні» за часовим поясом користувача.
- **Якість коду:** читабельність важливіша за «розумні» абстракції; єдиний стиль (`.editorconfig`, ESLint, Prettier).

## 13. Підготовка до захисту

7. Найскладніша помилка й як її знайшли.
8. Що змінили після реального використання.

## 16. Ризики та рішення

| Ризик | Рішення |
|---|---|
| Зсув дедлайнів на день через часові пояси | `Deadline` як `DateOnly`; «сьогодні» обчислюється за `TimeZoneId` користувача через `IClock` |
| Зламаний порядок карток у kanban | Позиції як дробові числа/інтервали з періодичним перенумеруванням; транзакційне оновлення |
| XSS через Markdown | Санітизація на фронтенді, без сирого HTML; тест на шкідливий Markdown |
| Контейнер `api` стартує раніше за БД | `depends_on` з `service_healthy` + повторні спроби підключення |
| Розростання обсягу | Пріоритети MUST/SHOULD/COULD; у разі браку часу відкидаємо SHOULD/COULD |
