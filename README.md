# Трекер задач (Task Tracker)

Багатокористувацький веб-застосунок для задач зі статусами, пріоритетами, дедлайнами, тегами, підзадачами та Markdown-нотатками, який можна переглядати списком, kanban-дошкою та календарем і налаштувати під свою роль.

Специфікація: [docs/spec/SPEC.md](docs/spec/SPEC.md). Технічна документація за модулями: [docs/README.md](docs/README.md).

## Реалізовані рівні та side quests

| Рівень | Що є |
|---|---|
| Basic | створення, список, зміна статусу, видалення з підтвердженням, збереження в PostgreSQL, валідація порожнього заголовка (UI і API), `CreatedAt` і час кожної зміни статусу |
| Standard | повний CRUD, пріоритет і дедлайн, теги, фільтри (статус, пріоритет, теги, дедлайн, діапазон дат, пошук, значення власного поля), сортування, пагінація, вигляд «Сьогодні», підсвітка прострочених, транзакції |
| Advanced | Kanban Web UI (drag-and-drop, оптимістичні оновлення), підзадачі, Markdown-нотатки, multi-user, календар (місяць/тиждень) |
| Твіст | шаблони профілів і власні поля |
| Додатково | світла/темна тема, клавіатурне перетягування, оптимістичний контроль конкурентності (`xmin`), демо-дані |

Не реалізовано з COULD: експорт у CSV (FR-P6).

## Особистий твіст: трекер під будь-яку роль

Під час реєстрації (або пізніше в налаштуваннях) обирається **шаблон профілю**: Універсальний, Студент, Фрілансер, Тренування. Шаблон додає набір тегів і власних полів (наприклад, «Предмет» та «Оцінка» для студента). Наявні дані не видаляються, дублікати за назвою пропускаються. Крім шаблонів, можна створювати власні поля (текст, число, прапорець, дата) і змінювати їхній порядок.

**Чому так:** більшість трекерів змушують людину підлаштовуватися під інструмент. Тут інструмент підлаштовується під людину, і при цьому лишається простим, бо додаткові поля необов'язкові.

## Запуск

Потрібні лише Docker і Docker Compose.

```bash
cp .env.example .env
```

Відкрийте `.env` і замініть усі значення `change-me…` (мінімум `POSTGRES_PASSWORD` і `JWT__Secret`). Потім:

```bash
docker compose up --build
```

Застосунок відкриється на `http://localhost:8080` (порт змінюється через `WEB_PORT`).

### Змінні середовища

| Змінна | Призначення | За замовчуванням |
|---|---|---|
| `POSTGRES_DB`, `POSTGRES_USER` | база даних і користувач | `tasktracker` |
| `POSTGRES_PASSWORD` | пароль БД (**обов'язково**, без `;`) | немає |
| `JWT__Secret` | ключ підпису JWT, щонайменше 32 символи (**обов'язково**) | немає |
| `JWT__ExpiresMinutes` | час життя токена | `60` |
| `SEED_DEMO` | `true` створює демо-користувача з задачами | `false` |
| `SEED_DEMO_EMAIL`, `SEED_DEMO_PASSWORD` | дані демо-акаунта (потрібні, якщо `SEED_DEMO=true`) | немає |
| `WEB_PORT` | порт застосунку на хості | `8080` |
| `DB_PORT` | порт PostgreSQL на `127.0.0.1` | `5432` |

Секретів у репозиторії немає: у git потрапляє лише `.env.example`, а `.env` ігнорується.

### Демо-акаунт

Задайте `SEED_DEMO=true`, `SEED_DEMO_EMAIL` і `SEED_DEMO_PASSWORD` у `.env` і запустіть застосунок. Буде створено користувача зі шаблоном «Студент» і десятком реалістичних задач (різні статуси, пріоритети, дедлайни, теги, підзадачі, нотатки). Повторний запуск нічого не дублює.

### Розробка: БД у Docker, api і web локально

```bash
docker compose up db -d
```

API (потрібен .NET 9 SDK; змінні можна взяти з `.env`):

```bash
cd backend
export ConnectionStrings__Default="Host=localhost;Port=5432;Database=tasktracker;Username=tasktracker;Password=<POSTGRES_PASSWORD>"
export Jwt__Secret="<JWT__Secret>"
export ASPNETCORE_ENVIRONMENT=Development
dotnet run --project src/TaskTracker.Api --urls http://localhost:8080
```

Міграції застосовуються при старті. Swagger: `http://localhost:8080/swagger` (лише в Development).

Frontend (Node 22):

```bash
cd frontend
npm install
npm run dev
```

Dev-сервер на `http://localhost:5173` проксує `/api` на `http://localhost:8080` (змінюється через `VITE_API_PROXY`), а API в Development дозволяє CORS для цього походження.

Нова міграція EF Core:

```bash
cd backend
dotnet tool restore
dotnet tool run dotnet-ef migrations add <Name> --project src/TaskTracker.Infrastructure --output-dir Persistence/Migrations
```

## 5 найкорисніших дій і гарячих клавіш

1. **Enter** у полі «Додати задачу…» миттєво створює задачу (на сторінці «Сьогодні» з дедлайном на сьогодні).
2. **Перетягування** картки на дошці змінює статус і порядок; з клавіатури: Tab до ручки ⠿, **Пробіл** підняти, **стрілки** перемістити, **Пробіл** опустити, **Esc** скасувати.
3. **Esc** закриває вікно деталей; **Tab** не виходить за межі відкритого вікна.
4. Перемикач **Список · Kanban · Календар** запам'ятовує вибір, а фільтри діють у всіх трьох виглядах.
5. У календарі задачу можна перетягнути на іншу дату, щоб змінити дедлайн; задачі без дати лежать у панелі «Без дати».

## Модель даних (коротко)

- **Користувач** має email (унікальний, нижній регістр), хеш пароля, ім'я, часовий пояс і шаблон профілю.
- **Задача** належить користувачу. Обов'язкова лише назва (1–200 символів); решта (опис, Markdown-нотатки, дедлайн, теги) необов'язкова. Дедлайн зберігається як календарна дата без часу, щоб часові пояси не зсували його на день. Позиція в колонці дробова, щоб картку можна було вставити між двома іншими без оновлення решти.
- **Підзадачі** (до 50, один рівень), **теги** (унікальні в межах користувача без урахування регістру) і **значення власних полів** прив'язані до задачі; **історія статусів** фіксує кожен перехід із часом.
- **Власне поле** має назву та тип, який не змінюється після створення, щоб збережені значення не змінили сенс. Значення зберігаються текстом і перевіряються за типом.

## Цілісність даних

- **Транзакції.** Кожна операція завершується одним `SaveChanges`, який EF Core виконує в одній транзакції PostgreSQL. Зміна статусу й запис переходу, перенесення картки, застосування шаблону зберігаються цілком або зовсім.
- **Міграції.** Схему створюють міграції EF Core, які `api` застосовує при старті. Повторний запуск безпечний, а старт чекає на БД із повторними спробами.
- **Ізоляція користувачів.** Усі запити до задач, тегів і полів фільтруються за `UserId` на рівні репозиторію. Чужий ресурс виглядає як неіснуючий (`404`), а прив'язати чужий тег до своєї задачі не можна.
- **Конкурентність.** Колонка `xmin` PostgreSQL слугує токеном: якщо задачу змінили між читанням і записом, повертається `409`, а не мовчазне перезаписування.
- **Цілісність у БД.** Зовнішні ключі й каскадні правила: видалення задачі прибирає підзадачі, зв'язки з тегами, переходи та значення полів; видалення тега чи поля чіпає лише зв'язки та значення. Унікальні індекси на email та (користувач, назва тега/поля).

## Архітектура

```text
                 HTTP / JSON
  React (nginx) ───────────────► TaskTracker.Api            контролери, помилки → RFC 7807, JWT
                                        │
                                        ▼
                                TaskTracker.Application     сценарії, DTO, валідатори, інтерфейси
                                        │                   (IUserRepository, ITaskRepository, IClock, ...)
                                        ▼
                                TaskTracker.Domain          сутності, інваріанти, enum-и (без залежностей)
                                        ▲
                                        │ реалізує інтерфейси
                                TaskTracker.Infrastructure  EF Core, міграції, репозиторії, JWT, BCrypt, сид
                                        │
                                        ▼
                                   PostgreSQL 16
```

Залежності спрямовані лише всередину: `Api → Application → Domain` та `Infrastructure → Application → Domain`. Бізнес-правила (заголовок, статуси, «прострочено») живуть у Domain, тож їх можна тестувати без БД.

Фільтри та сортування задач написані як звичайний LINQ у `Application/Filtering`: EF Core перетворює їх на SQL, а юніт-тести виконують той самий код над списком у пам'яті.

## Тести

Backend (інтеграційні тести самі запускають PostgreSQL через Testcontainers, тому потрібен запущений Docker):

```bash
cd backend
dotnet test
```

Окремо: `dotnet test tests/TaskTracker.Domain.Tests`, `tests/TaskTracker.Application.Tests`, `tests/TaskTracker.Api.IntegrationTests`.

Frontend:

```bash
cd frontend
npm test
npm run lint
npm run build
```

CI (`.github/workflows/ci.yml`) запускає ті самі команди та перевіряє збірку Docker-образів.
